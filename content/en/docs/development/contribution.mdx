# Contribution Guide

Thank you for your interest in contributing to RedisHub! We welcome contributions to help improve the project.

## Where the Code Lives

The GitHub repository is a **read-only mirror**. Development happens in a private upstream
repository, and every push upstream force-updates the mirror. Pull requests still work as usual;
two things are different:

- **Your pull request is not merged with the green button.** A maintainer lands your commits
  upstream and the mirror carries them back, at which point GitHub marks your PR as merged, with you
  as the author.
- **Do not push a branch to the GitHub repository**, even if you have write access: the next sync
  deletes it. Work on a fork.

> [!NOTE]
> The repository's [`CONTRIBUTING.md`](https://github.com/tradalab/redishub/blob/main/CONTRIBUTING.md)
> says the same thing. That is the copy GitHub puts in front of you when you open a pull request.

A typo fix or a small bug fix needs no issue first. For anything larger (a new feature, a new
dependency, a change to the IPC contract), open a [GitHub Issue](https://github.com/tradalab/redishub/issues)
and get agreement before you write the code.

## Contribution Workflow

1. **Fork**: fork `tradalab/redishub` on GitHub and clone your fork.
2. **Branching**: Create a feature branch off of `main`.
3. **Coding Standards**:
    - **Go**: Follow `gofmt` and standard Go idioms.
    - **Frontend**: Use Tailwind CSS for styling and TypeScript for typed props.
    - **IPC**: Edit `idl/app.proto` and run `make generate` - never hand-edit the generated `internal/handler` / `internal/types` / `shell/api/index.ts`. See [Adding IPC Commands](/docs/development/extending).
4. **Testing**:
    - Ensure your changes run correctly in development mode using `make dev`.
    - Run `make lint` and `make test` before opening the PR. CI runs `scorix build`, `scorix test`
      and `scorix lint` on the PR; `make test` and `make lint` are the local equivalents.
5. **Commit Messages**: one short line in the form `<type>: <short description>`, with no body
   (e.g. `fix: the graph survives a resize`).
    - `feat:`: New feature.
    - `fix:`: Bug fix.
    - `docs:`: Documentation changes.
    - `refactor:`: Code changes that neither fix a bug nor add a feature.
    - `chore:`: Maintenance tasks (e.g., updating dependencies).

## Review Process

1. Push the branch to your fork and open a pull request against `main`.
2. Provide a clear description of the problem solved or the feature added, and link any relevant issues.
3. CI runs on the PR, and review happens in the PR. Push follow-up commits to your branch as usual.
4. On approval a maintainer lands it upstream; the mirror follows and the PR shows as merged.

## Communication

If you have questions about the project or want to discuss a new feature, feel free to open a **GitHub Issue** or start a **Discussion**.
