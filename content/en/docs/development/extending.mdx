# Adding a New IPC Command

RedisHub bridges the Go backend and the Next.js frontend with an **Inter-Process Communication (IPC)**
layer that is **generated from a Protobuf contract**. Commands follow the pattern `service:method`
in lowercase kebab case (e.g. `client:connect` from the proto `rpc` `client.Connect`, or
`client:load-key-detail` from `client.LoadKeyDetail`).

You do **not** hand-write the command router. `internal/handler/handler.go` and
`internal/types/types.go` are generated - each carries a `// Code generated by scorix. DO NOT EDIT.`
header. To add a command you edit the proto, validate, regenerate, then fill in the generated logic stub.
The generated `docs/ipc-surface.md` lists every command and event the proto declares.

---

## Step 1: Declare the Contract in `idl/app.proto`

Add the request/response messages and an `rpc` to the relevant `service`. Use `returns (Empty)` for a
fire-and-forget call, a response message for a request/response call, or `returns (stream …)` for a
server-streaming command (like `monitor:start` or `console:exec`).

```proto
message MyActionReq {
  string connection_id  = 1;
  int32  database_index = 2;
  string custom_param   = 3;
}

message MyActionRes {
  string result = 1;
}

service client {
  // ... existing rpcs
  rpc MyAction(MyActionReq) returns (MyActionRes);
}
```

---

## Step 2: Validate the Contract

```bash
scorix validate
```

This reads `scorix.yaml`, the proto and the SQL schema and reports problems without writing anything.
Errors stop `generate`; warnings mean it would run and produce something you probably did not intend.

---

## Step 3: Regenerate Handlers, Types & Models

```bash
make generate
```

This runs `scorix generate proto` and `scorix generate model`. From the proto it regenerates the Go
handler (`internal/handler/handler.go`), the Go types (`internal/types`), the typed events
(`internal/events`), the typed frontend client (`shell/api/index.ts`) and its types
(`shell/types/index.ts`), and `docs/ipc-surface.md`. It also writes a logic stub for every new rpc.
From `idl/schema.sql` it regenerates the sqlx models (`internal/model/*_model_gen.go`) and
`idl/schema_gen.go`. The new command is now registered on both sides.

---

## Step 4: Implement the Business Logic

Open the generated stub `internal/logic/<service>/<action>_logic.go` (here
`internal/logic/client/my_action_logic.go`) and fill in the method. You do not create this file by
hand; `make generate` writes it once and never overwrites it afterwards (only `--force` does). The
generated handler constructs your logic with `(ctx, svcCtx)` and calls the method with the decoded
request:

```go
package client

import (
	"context"

	"github.com/tradalab/rdms/internal/svc"
	"github.com/tradalab/rdms/internal/types"
)

type MyActionLogic struct {
	ctx    context.Context
	svcCtx *svc.ServiceContext
}

func NewMyActionLogic(ctx context.Context, svcCtx *svc.ServiceContext) *MyActionLogic {
	return &MyActionLogic{ctx: ctx, svcCtx: svcCtx}
}

func (l *MyActionLogic) MyAction(params *types.MyActionReq) (*types.MyActionRes, error) {
	// 1. Resolve the Redis client via l.svcCtx.RedisManager
	// 2. Perform the operation
	// 3. Return the typed response and error
	return &types.MyActionRes{Result: "ok"}, nil
}
```

> [!NOTE]
> For a **server-streaming** rpc, the generated handler wires an `app.Sink[T]`; implement
> `MyAction(params *types.MyActionReq, out app.Sink[types.MyEvent]) error` and push frames with
> `out.Send(...)`. See `internal/logic/monitor/start_logic.go` for a worked example.

---

## Step 5: Call from the Frontend

Use the generated, typed client in `shell/api/index.ts`. The proto `rpc` `client.MyAction` is exposed
as `client.myAction(params)` (wire name `client:my-action`):

```typescript
import { client } from "@/api";

const res = await client.myAction({
  connection_id: "123",
  database_index: 0,
  custom_param: "hello",
});
```

Streaming commands return an async-iterable instead - e.g. `monitor.start(params)` yields frames
(`for await (const frame of monitor.start(...))`). Under the hood everything goes through the
auto-injected `window.scorix` bridge (`scorix.invoke` / `scorix.serverStream`).

> [!TIP]
> Keep the proto the single source of truth - changing a field means editing `idl/app.proto` and
> re-running `make generate`, never hand-editing the generated `internal/handler`, `internal/types`,
> `internal/events` or `shell/api/index.ts`.

---

## Adding a Table Column

The database schema has two parts, and a new column needs both:

1. **Add the column to `idl/schema.sql`** and run `make generate`. This is what the model generator
   reads: it regenerates `internal/model/<table>_model_gen.go` and `idl/schema_gen.go`.
2. **Add a numbered goose migration in `idl/migration/`.** `schema.sql` is not replayed on a database
   that already exists, so without a migration the column never reaches existing installs. Do not edit
   `00001_baseline.sql`: it is frozen, every install is already stamped past it, and an edit there never
   runs again.

Follow `00003_color.go` and `00004_connection_tags.go`. A Go migration registers itself and adds the
column with `scorixsqlx.AddColumn`:

```go
package migration

import (
	"context"
	"database/sql"

	"github.com/pressly/goose/v3"
	scorixsqlx "github.com/tradalab/scorix/module/sqlx"
)

func init() {
	goose.AddNamedMigrationContext("00005_my_column.go", upMyColumn, downMyColumn)
}

func upMyColumn(ctx context.Context, tx *sql.Tx) error {
	return scorixsqlx.AddColumn(ctx, tx, "connection", "my_column", "TEXT NOT NULL DEFAULT ''")
}

func downMyColumn(context.Context, *sql.Tx) error { return nil }
```

Never hand-edit `internal/model/*_model_gen.go` or `idl/schema_gen.go`. Custom model code (extra
queries, helper methods) goes in `internal/model/<table>_model.go`, which the generator creates once
and then leaves alone.

---

## Checking for Drift

Both generators have a `--check` flag that verifies the generated code is in sync without writing
anything (meant as a CI drift guard):

```bash
scorix generate proto --check
scorix generate model --check
```
