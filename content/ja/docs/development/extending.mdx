# 新しい IPC コマンドの追加

RedisHub は、**Protobuf コントラクトから生成される** **プロセス間通信 (IPC)** レイヤーによって、Go バックエンドと Next.js フロントエンドを橋渡しします。コマンドは小文字ケバブケースの `service:method` パターンに従います (例: proto の `rpc` `client.Connect` からは `client:connect`、`client.LoadKeyDetail` からは `client:load-key-detail`)。

コマンドルーターを手作業で記述することは**ありません**。`internal/handler/handler.go` と `internal/types/types.go` は生成されるファイルであり、それぞれに `// Code generated by scorix. DO NOT EDIT.` ヘッダーが付いています。コマンドを追加するには、proto を編集し、検証し、再生成してから、生成されたロジックのスタブを埋めます。生成される `docs/ipc-surface.md` には、proto が宣言するすべてのコマンドとイベントが一覧されています。

---

## ステップ 1: `idl/app.proto` でコントラクトを宣言する

該当する `service` に、リクエスト/レスポンスメッセージと `rpc` を追加します。fire-and-forget な呼び出しには `returns (Empty)` を、リクエスト/レスポンス型の呼び出しにはレスポンスメッセージを、サーバーストリーミングコマンド (`monitor:start` や `console:exec` など) には `returns (stream …)` を使用します。

```proto
message MyActionReq {
  string connection_id  = 1;
  int32  database_index = 2;
  string custom_param   = 3;
}

message MyActionRes {
  string result = 1;
}

service client {
  // ... existing rpcs
  rpc MyAction(MyActionReq) returns (MyActionRes);
}
```

---

## ステップ 2: コントラクトを検証する

```bash
scorix validate
```

これは `scorix.yaml`、proto、SQL スキーマを読み込み、何も書き込まずに問題を報告します。エラーがあると `generate` は止まります。警告は、実行はされるものの意図しないものが生成される可能性が高いことを意味します。

---

## ステップ 3: ハンドラー、型、モデルを再生成する

```bash
make generate
```

これは `scorix generate proto` と `scorix generate model` を実行します。proto からは、Go ハンドラー (`internal/handler/handler.go`)、Go の型 (`internal/types`)、型付きイベント (`internal/events`)、型付きのフロントエンドクライアント (`shell/api/index.ts`) とその型 (`shell/types/index.ts`)、そして `docs/ipc-surface.md` が再生成されます。新しい rpc ごとにロジックのスタブも書き出されます。`idl/schema.sql` からは sqlx モデル (`internal/model/*_model_gen.go`) と `idl/schema_gen.go` が再生成されます。これで新しいコマンドが両側に登録されます。

---

## ステップ 4: ビジネスロジックを実装する

生成されたスタブ `internal/logic/<service>/<action>_logic.go` (この例では `internal/logic/client/my_action_logic.go`) を開き、メソッドを実装します。このファイルを手作業で作成する必要はありません。`make generate` が一度だけ書き出し、その後は上書きしません (`--force` を指定した場合のみ上書きします)。生成されたハンドラーは、`(ctx, svcCtx)` を使ってロジックを構築し、デコードされたリクエストとともにメソッドを呼び出します。

```go
package client

import (
	"context"

	"github.com/tradalab/rdms/internal/svc"
	"github.com/tradalab/rdms/internal/types"
)

type MyActionLogic struct {
	ctx    context.Context
	svcCtx *svc.ServiceContext
}

func NewMyActionLogic(ctx context.Context, svcCtx *svc.ServiceContext) *MyActionLogic {
	return &MyActionLogic{ctx: ctx, svcCtx: svcCtx}
}

func (l *MyActionLogic) MyAction(params *types.MyActionReq) (*types.MyActionRes, error) {
	// 1. Resolve the Redis client via l.svcCtx.RedisManager
	// 2. Perform the operation
	// 3. Return the typed response and error
	return &types.MyActionRes{Result: "ok"}, nil
}
```

> [!NOTE]
> **サーバーストリーミング** の rpc の場合、生成されたハンドラーは `app.Sink[T]` を接続します。`MyAction(params *types.MyActionReq, out app.Sink[types.MyEvent]) error` を実装し、`out.Send(...)` でフレームをプッシュします。実際の例については `internal/logic/monitor/start_logic.go` を参照してください。

---

## ステップ 5: フロントエンドから呼び出す

`shell/api/index.ts` にある生成済みの型付きクライアントを使用します。proto の `rpc` `client.MyAction` は `client.myAction(params)` として公開されます (ワイヤー名は `client:my-action`)。

```typescript
import { client } from "@/api";

const res = await client.myAction({
  connection_id: "123",
  database_index: 0,
  custom_param: "hello",
});
```

ストリーミングコマンドは代わりに async-iterable を返します。例えば `monitor.start(params)` はフレームを yield します (`for await (const frame of monitor.start(...))`)。内部では、すべての処理が自動注入される `window.scorix` ブリッジ (`scorix.invoke` / `scorix.serverStream`) を経由します。

> [!TIP]
> proto を唯一の信頼できる情報源として保ちましょう。フィールドを変更する場合は `idl/app.proto` を編集して `make generate` を再実行します。生成された `internal/handler`、`internal/types`、`internal/events`、`shell/api/index.ts` を手作業で編集してはいけません。

---

## テーブルへのカラム追加

データベーススキーマは 2 つの部分からなり、新しいカラムには両方が必要です。

1. **`idl/schema.sql` にカラムを追加**して `make generate` を実行します。モデルジェネレーターが読むのはこのファイルで、`internal/model/<table>_model_gen.go` と `idl/schema_gen.go` が再生成されます。
2. **`idl/migration/` に番号付きの goose マイグレーションを追加します。** `schema.sql` は既存のデータベースには再適用されないため、マイグレーションがなければカラムは既存のインストールに届きません。`00001_baseline.sql` は編集しないでください。これは凍結されており、すべてのインストールはすでにこれを通過済みとして記録されているため、そこへの編集は二度と実行されません。

`00003_color.go` と `00004_connection_tags.go` に倣ってください。Go のマイグレーションは自身を登録し、`scorixsqlx.AddColumn` でカラムを追加します。

```go
package migration

import (
	"context"
	"database/sql"

	"github.com/pressly/goose/v3"
	scorixsqlx "github.com/tradalab/scorix/module/sqlx"
)

func init() {
	goose.AddNamedMigrationContext("00005_my_column.go", upMyColumn, downMyColumn)
}

func upMyColumn(ctx context.Context, tx *sql.Tx) error {
	return scorixsqlx.AddColumn(ctx, tx, "connection", "my_column", "TEXT NOT NULL DEFAULT ''")
}

func downMyColumn(context.Context, *sql.Tx) error { return nil }
```

`internal/model/*_model_gen.go` や `idl/schema_gen.go` を手作業で編集してはいけません。独自のモデルコード (追加のクエリやヘルパーメソッド) は `internal/model/<table>_model.go` に書きます。このファイルはジェネレーターが一度だけ作成し、その後は手を付けません。

---

## ドリフトの確認

どちらのジェネレーターにも `--check` フラグがあり、何も書き込まずに生成コードが同期しているかを検証します (CI のドリフトガード向けです)。

```bash
scorix generate proto --check
scorix generate model --check
```
