# コントリビューションガイド

RedisHub へのコントリビューションに関心をお寄せいただき、ありがとうございます。プロジェクトの改善に役立つコントリビューションを歓迎します。

## コードの所在

GitHub のリポジトリは**読み取り専用のミラー**です。開発はプライベートなアップストリームリポジトリで
行われ、同期のたびにミラーは強制的に上書きされます。そのため GitHub に push したブランチや
プルリクエストはマージできず、次の同期で消えてしまいます。

- **メンテナー**はアップストリームで作業します。`main` からブランチを切り、レビューを経て取り込みます。
- **それ以外の方**は [GitHub Issue](https://github.com/tradalab/redishub/issues) に変更内容を書いて
  ください（パッチや fork へのリンクも歓迎します）。メンテナーがアップストリームに取り込みます。

> [!NOTE]
> 同じ内容がリポジトリの [`CONTRIBUTING.md`](https://github.com/tradalab/redishub/blob/main/CONTRIBUTING.md)
> にもあります。プルリクエストを作成するときに GitHub が表示するのはそちらで、常に最新に保たれています。

## コントリビューションのワークフロー

1. **クローン**: `git clone https://github.com/tradalab/redishub.git`（ミラーは公開されており、常に最新です）。
2. **ブランチ作成**: `main` からフィーチャーブランチを作成します。
3. **コーディング規約**:
    - **Go**: `gofmt` と標準的な Go のイディオムに従います。
    - **フロントエンド**: スタイリングには Tailwind CSS を、型付き props には TypeScript を使用します。
    - **IPC**: `proto/app.proto` を編集して `make generate` を実行します。生成された `handler.go` / `types.go` / `shell/api/index.ts` を手作業で編集してはいけません。
4. **テスト**:
    - `make dev` を使用して、変更が開発モードで正しく動作することを確認します。
    - 変更を提出する前に `make lint` と `make test` を実行します。
5. **コミットメッセージ**: [Conventional Commits](https://www.conventionalcommits.org/) 形式に従い、内容が分かるコミットメッセージを使用します: `<type>(<scope>): <description>`。
    - `feat:`: 新機能。
    - `fix:`: バグ修正。
    - `docs:`: ドキュメントの変更。
    - `refactor:`: バグ修正でも機能追加でもないコード変更。
    - `chore:`: メンテナンス作業 (依存関係の更新など)。

## レビューのプロセス

1. メンテナーがアップストリームで `main` ブランチをターゲットとするレビュー依頼を作成します。Issue 経由で
   届いたコントリビューションも同じ流れで取り込まれます。
2. 解決した問題や追加した機能について、明確な説明を記載します。
3. 関連する Issue やディスカッションへのリンクを添えます。
4. コードがレビューされ承認されるとメンテナーがマージし、数分以内に GitHub のミラーへ反映されます。

## コミュニケーション

プロジェクトについて質問がある場合や、新機能について議論したい場合は、お気軽に **GitHub Issue** を作成するか、**Discussion** を開始してください。
