# コントリビューションガイド

RedisHub へのコントリビューションに関心をお寄せいただき、ありがとうございます。プロジェクトの改善に役立つコントリビューションを歓迎します。

## コードの所在

GitHub のリポジトリは**読み取り専用のミラー**です。開発はプライベートなアップストリームリポジトリで
行われ、アップストリームへの push のたびにミラーは強制的に上書きされます。プルリクエストは通常どおり使えますが、
2 つの点が異なります。

- **プルリクエストは緑のボタンではマージされません。** メンテナーがあなたのコミットをアップストリームに取り込み、
  ミラーがそれを反映した時点で、GitHub はあなたを作者として PR をマージ済みにします。
- **GitHub のリポジトリにブランチを push しないでください。** 書き込み権限があっても、次の同期で削除されます。
  fork で作業してください。

> [!NOTE]
> 同じ内容がリポジトリの [`CONTRIBUTING.md`](https://github.com/tradalab/redishub/blob/main/CONTRIBUTING.md)
> にもあります。プルリクエストを作成するときに GitHub が表示するのはそちらです。

タイポの修正や小さなバグ修正なら、先に Issue を立てる必要はありません。それより大きな変更（新機能、新しい
依存関係、IPC コントラクトの変更）は、コードを書く前に [GitHub Issue](https://github.com/tradalab/redishub/issues)
を作成して合意を得てください。

## コントリビューションのワークフロー

1. **Fork**: GitHub で `tradalab/redishub` を fork し、その fork をクローンします。
2. **ブランチ作成**: `main` からフィーチャーブランチを作成します。
3. **コーディング規約**:
    - **Go**: `gofmt` と標準的な Go のイディオムに従います。
    - **フロントエンド**: スタイリングには Tailwind CSS を、型付き props には TypeScript を使用します。
    - **IPC**: `idl/app.proto` を編集して `make generate` を実行します。生成された `internal/handler` / `internal/types` / `shell/api/index.ts` を手作業で編集してはいけません。[IPC コマンドの追加](/ja/docs/development/extending) を参照してください。
4. **テスト**:
    - `make dev` を使用して、変更が開発モードで正しく動作することを確認します。
    - PR を作成する前に `make lint` と `make test` を実行します。CI は PR 上で `scorix build`、`scorix test`、
      `scorix lint` を実行します。`make test` と `make lint` はそのローカル版です。
5. **コミットメッセージ**: `<type>: <short description>` 形式の短い 1 行で、本文は付けません
   (例: `fix: the graph survives a resize`)。
    - `feat:`: 新機能。
    - `fix:`: バグ修正。
    - `docs:`: ドキュメントの変更。
    - `refactor:`: バグ修正でも機能追加でもないコード変更。
    - `chore:`: メンテナンス作業 (依存関係の更新など)。

## レビューのプロセス

1. ブランチを自分の fork に push し、`main` に対してプルリクエストを作成します。
2. 解決した問題や追加した機能について明確な説明を記載し、関連する Issue へのリンクを添えます。
3. PR 上で CI が実行され、レビューも PR 上で行われます。追加のコミットは通常どおりブランチに push します。
4. 承認されるとメンテナーがアップストリームに取り込み、ミラーに反映されて PR はマージ済みと表示されます。

## コミュニケーション

プロジェクトについて質問がある場合や、新機能について議論したい場合は、お気軽に **GitHub Issue** を作成するか、**Discussion** を開始してください。
